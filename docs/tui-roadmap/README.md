# План развития TUI

**Русский** | [English](README.en.md)

Состояние на 10 ноября 2026 года: Go-клиент `0.2.0-preview.12`.
Этот документ — общий список различий с Electron-лаунчером и интерфейсом dsh,
а также порядок их переноса. Пункты плана не означают, что функции уже доступны.

## Цель и порядок работы

Терминальный Linux-клиент на Go + Bubble Tea с функциональными эквивалентами
лаунчера, dsh и плагинов. Совпадение возможностей важнее копирования веб-вёрстки.
Серверные JS-плагины продолжает исполнять dsh; Go отвечает за терминальный интерфейс.

Двигаемся небольшими шагами: одна законченная возможность, проверка, просмотр
пользователем, затем следующий шаг. Каждый этап ниже разбивается на такие шаги.
При изменении интерфейса показываем снимок настоящего приложения. Публичное
демо Pages отключено; живой просмотр возможен через приватный Codespaces.

## Что уже есть

- Верхнее меню «Файл / Вид / Справка», модальные настройки TUI; сохраняются параметры мыши и истории ввода.
- Боковая навигация, панели, ввод и история локального черновика, мышь и прокрутка.
- Подключение к dsh, чтение настроек с маскированием секретов.
- Вопросы агента: варианты, множественный выбор, многострочный ответ, пропуск, набор вопросов, тайм-аут и продолженный ответ.
- Окна разрешений: причина, аргументы, разрешение на один вызов/отказ, F7, отмена и восстановление запросов.
- Карточки инструментов: состояние, аргументы, результат/ошибка, раскрытие мышью или F6 → Enter; восстановление из истории.
- Текстовый чат в сессии: отправка, поток ответа, отмена, восстановление чтения без автоматической повторной отправки.
- Создание, список и подключение сессий; подтверждённые сервером режимы и команды целей.
- Запуск установленного dsh через `--start`, предложение предустановки dshmarket.
- Маркет: каталог, поиск, установленные пакеты, подтверждаемые установка,
  обновление и удаление; прогресс из API.
- Go/PTY/CI-проверки и конфигурация живого Codespaces с настоящим dsh.

Без подключения ввод остаётся локальным. Чат проверен с настоящим dsh и
контролируемым локальным провайдером; это проверка протокола, а не реальной LLM.
Облачная LLM для стенда не подключена. Приёмка этапа 2 на настоящей облачной
модели ожидает действующего доступа. Полные диалоги инструментов относятся к этапу 3.

## Этапы и критерии готовности

1. **Верхнее меню и настройки TUI — выполнено в preview.8.** Меню «Файл», «Вид», «Справка»;
   настройки TUI открываются сверху и исчезают из боковой навигации.
   Настройки dsh остаются отдельным разделом. Начальные редактируемые параметры —
   мышь и история ввода; сохраняем выбор, показываем сведения о клиенте и справку.
   Готово: меню доступно с клавиатуры и мышью, работает на узком терминале,
   открытие/закрытие сохраняет страницу, черновик и фокус.
2. **Минимальный настоящий чат — реализован в preview.9; приёмка облачной LLM ожидает доступа.** Отправка в сессию, потоковый текст ответа,
   отмена, ошибки и переподключение без повторной отправки принятого сообщения.
   Готово: на настоящем dsh получен ответ модели; выход восстанавливает терминал.
3. **Инструменты и взаимодействие — первый шаг выполнен в preview.10.** Карточки вызовов и результатов, ошибки, отмена, раскрытие вывода и восстановление истории; проверено чтение файла настоящим dsh. Разрешения выполнены в preview.11: явный разовый допуск/отказ, отмена, переподключение, история решений. Вопросы выполнены в preview.12: варианты и свободный ввод, наборы, тайм-ауты, восстановление и поздние ответы. Следующие шаги:
   базовое управление очередью и вмешательством в выполнение.
   Готово: агент выполняет проверочную задачу с инструментом; отказ и отмена
   корректно отражаются в dsh, а ввод вопроса не уходит как обычное сообщение.
4. **История и сессии.** Чтение переписки, поиск, переименование, ветвление,
   поддерживаемые dsh операции архива; Markdown и сворачиваемые детали.
   Готово: повторное подключение восстанавливает настоящую историю без дублей.
5. **Модели и настройки dsh.** Авторизация провайдеров, выбор модели,
   формы по схеме и сохранение с проверкой ревизий; секреты не показываются
   в переписке и журнале. Изменения, требующие перезапуска, явно обозначаются.
   Готово: выбранная модель применяется к сессии; конфликт настройки не затирает
   чужое изменение. Для реальной проверки нужен действующий доступ к провайдеру.
6. **Планы, цели и пресеты.** Развиваем существующие режимы: просмотр и
   согласование плана, редактирование цели, состояние выполнения и выбор пресета.
   Готово: состояние переживает переподключение и совпадает с состоянием dsh.
7. **Рабочая область и ввод.** Последовательно добавляем многострочный ввод,
   файлы/вложения, дерево и просмотр документов, терминальную панель.
   Для браузерных функций отдельно определяем терминальные сценарии и пределы
   поддержки; произвольный веб-экран не считаем автоматически перенесённым.
   Готово: агент получает выбранный файл, а пользователь видит результат в своей
   рабочей области; клавиши и фокус не конфликтуют между панелями.
8. **Общая поддержка плагинов.** Каталог возможностей, формы по доступным схемам,
   команды и общие представления результатов. Затем минимальный декларативный
   контракт и SDK: сначала форма и действие, далее таблицы и статусы.
   Готово: два разных плагина используют одни компоненты без отдельного Go-экрана;
   неподдерживаемые функции явно обозначены.
9. **Маркет и специальные адаптеры.** Доводим управление пакетами; добавляем
   специальные экраны только для функций, не покрытых общим контрактом.
   Готово: проверены отказ, конфликт, восстановление состояния после перезапуска;
   для каждого заявленного адаптера есть сценарий с настоящим API плагина.
10. **Подагенты, задания и расписания.** По одному экрану переносим наблюдение,
    доступные команды управления, результаты и ссылки на связанные сессии.
    Готово: состояния читаются из dsh и восстанавливаются после подключения.
11. **Установка и жизненный цикл dsh.** Обнаружение Node/dsh, предложение
    установки dsh с живым прогрессом, ошибки, повтор и управление своим процессом.
    Готово: новый профиль проходит установку и запуск; чужой dsh не останавливается
    при выходе клиента.
12. **Обновления и откат.** Отдельные небольшие шаги для dsh и Go-клиента:
    проверка версии, описание изменений, установка и восстановление прежней версии.
    Готово: неудачное обновление имеет проверенный путь восстановления.
13. **Диагностика и уведомления.** Журнал dsh, экспорт отчёта с маскированием
    секретов, статус выполнения и применимые к терминалу уведомления.
    Готово: неисправность можно воспроизвести по отчёту без раскрытия ключей.
14. **Полировка и выпуск.** Темы и язык, поиск, панели, мышь, справка по клавишам,
    чистая установка готовых сборок и проверка на поддерживаемых Linux-системах.
    Готово: согласованы сценарии повседневной работы и список известных ограничений.

## Какие настройки Electron переносить

Применимы к TUI: история ввода, мышь, язык, цветовая тема, рабочая папка,
путь/профиль/порт своего dsh, обновления, журналы и уведомления, если соответствующая
функция уже реализована. Параметры запуска dsh добавляем на этапе 11, обновления —
на этапе 12. Шрифт и масштаб обычно задаёт терминал, браузерный масштаб — оболочка
живого стенда. Нереализованные настройки не выдаём за работающие.

Wayland/X11, Ozone, GPU Electron, Chromium sandbox, оконная геометрия,
сворачивание в трей, полноэкранный режим Electron и проверка орфографии Chromium
в настройки TUI не переносятся.

## Плагины: четыре уровня поддержки

1. **Без отдельного экрана.** Фоновые возможности и инструменты агента исполняются
   в dsh. Их результат виден через общий чат/инструменты после этапов 2–3.
2. **Общий интерфейс из существующих данных.** Настройки строятся по схемам dsh;
   команды — по доступным серверным описаниям. Это покрывает только функции,
   которые действительно предоставляет API. Веб-действия и собственные диалоги
   не превращаются в серверные команды автоматически.
3. **Декларативный интерфейс плагина.** Предлагаемый, пока не реализованный контракт:
   плагин описывает формы, таблицы, действия и статусы, а TUI их отображает.
   Нужны версия протокола, описание возможностей и проверка совместимости.
   JS-плагин может формировать эти данные; переписывать его сервер на Go не требуется.
4. **Специальный адаптер.** Для сложных сценариев — отдельное терминальное
   представление поверх API, как текущий маркет. Общие компоненты переиспользуются.
   Если подходящего API нет, сначала требуется расширение серверной части плагина.

Стратегия — сочетать все четыре уровня. Для каждого плагина фиксируем отдельно:
работу серверной части, настройки, команды и полноценный экран. Наличие одного
экрана или установленного пакета не означает полную совместимость плагина.
HTML/React произвольного плагина Bubble Tea автоматически не исполняет.

## Проверка каждого шага

- Проверки протокола и ошибок на управляемом HTTP-стенде; PTY-проверки клавиатуры,
  мыши, изменения размера и восстановления терминала.
- Для видимых изменений — настоящие снимки широкого и узкого терминала
  (включая 80×24 и минимальные 44×18), сохранение черновика и фокуса.
- Проверка с настоящим dsh/плагином для подключаемого адаптера. Фикстуры
  и тестовая LLM не служат доказательством работы настоящего агента.
- На Linux проверяем готовый бинарный файл; установочные Docker-сценарии TUI
  добавляем по мере появления установки. Существующие GUI Docker-сценарии
  запускаются только в CI по правилам CONTRIBUTING.md.
- Небольшой коммит в `feature/terminal-ui`, проверки CI и результат для просмотра;
  слияние и релиз остаются отдельными действиями.
